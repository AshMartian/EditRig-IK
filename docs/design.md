# EditRig IK companion — working design

## Intent
Build a companion Studio plugin for authoring procedural IK on existing rigs, including both Motor6D and skinned Bone chains. RigEdit remains independently installed; this project does not patch or depend on its private code. Dino Auto is the experimental rig; its current built-in IK setup is described below.

## Architecture
- A docked editor selects a model, identifies ordered Motor6D or Bone chains, displays them, and edits per-chain and per-joint settings. The editor visualizes local axes, limits, target and pole, warns about ambiguous or disconnected chains, and supports reversible preview.
- Versioned configuration belongs to the rig and contains explicit joint identity, rest frame, limit type and local axis, hinge lower/upper angles or swing cone and twist range, solver choice, iterations, tolerance, weight, target, pole, and update policy. Validate before saving or generating; do not silently replace malformed settings.
- A shared runtime exposes a documented API for loading a configuration, setting a target and pole, enabling/disabling and stepping the solver, querying diagnostics, and destroying/restoring state. Rig-specific adapters convert Bone or Motor6D animation transforms to a shared local rotation representation and apply results; ownership and animation update order must be explicit. Generated user scripts are thin examples referencing runtime modules, never opaque source blobs.
- Limits are evaluated in each joint's stored rest frame. Hinge is signed rotation around its configured local axis; ball limits split swing and twist. Solvers apply limits during each iteration, not only after convergence. Unreachable targets, straight-chain singularities, antiparallel directions and zero-length links require bounded, deterministic handling and diagnostics.

### Planned limit-frame editing

The current editor supports the joint-local X, Y and Z axes. Tilting the plane to an arbitrary orientation and rotating the allowed interval are separate operations: the first changes the actual solver axis, and the second shifts the signed lower and upper limits together. The editor can shift non-wrapping hinge intervals in 5° steps. `src/shared/LimitFrame.luau` provides basis and interval math, and the runtime chain reader accepts a versioned frame; arbitrary orientation is not yet exposed by the editor. Wrapped intervals are not supported by the current solver. Before exposing arbitrary orientation, propagate it through metadata, chain and actor snapshots, solver and input bindings, preview, and built-in constraints, and ensure older runtimes reject settings they cannot interpret rather than silently using an X/Y/Z axis. Retain identity behavior for existing settings. Independent directional ball swing limits also require solver and data-model work.

`src/shared/CircularHinge.luau` contains experimental, separately tested circular interval math using a start and positive width. It is not packaged or connected to the editor or solver. Seam-crossing support requires a new chain schema, compatible joint and actor version gates, preview and handle updates, and explicit rejection of unsupported built-in constraints until their attachment-frame behavior is verified in Play. A future foot-orientation control should rotate the requested ghost target separately from joint-limit editing, report position and orientation error, and preserve explicit sole and forward directions for surface alignment.

## Prototype and verification
Start with portable quaternion limit math and tests, then a working editor, runtime adapters and solver. The prototype is experimental: no claim of rig compatibility or glitch resolution until tested inside Studio on Dino Auto. Unit tests cover pure math, while Studio integration tests must cover transforms, actual poses, Animator interaction, frame ordering, both rig types, persistence, preview restoration and generated scripts. No automatic changes to the installed RigEdit plugin or live rig.

## Open decisions
Dino Auto's reproduction and the correct local limit axes remain unknown. Solver algorithm, default limits and initial UI layout remain design choices to verify against the real rig; they are not assumptions about existing behavior. No physical constraints are created merely to pretend that a custom solver respects limits.

## Dino Auto inspection (2026-11-07)
The experimental model is `Workspace.Dino Auto` in Prehistoric Rumble, place 93747181848349. Its legs are Motor6D chains, not Bone chains. Two enabled Transform IKControls under the Humanoid run from each `Leg 1` to its `Foot`; poles are assigned by the model script at runtime. A read-only descendant scan found no HingeConstraint or BallSocketConstraint in this model. The existing built-in IKControl is separate from the custom solver planned here, and would need explicit ownership arbitration before a custom solver drives the same joints.

`ProceduralModule:IkLegStep` initializes PreviousPos to world origin and moves targets in two discrete jumps, midpoint then endpoint, separated by 0.05 seconds. The outer script alternates legs on 0.5-second waits. A read-only edit-pose raycast on 2026-11-07 found no PreviousPos attribute and computed initial midpoint displacements of 6.968 studs left and 5.772 studs right; the sampled ground point was only about 1.648 studs from each current target. `tests/studio/DinoStepDiagnostic.integration.luau` repeats this calculation for the current pose and confirms the prototype smooth trajectory starts at the current target and ends at the sampled destination. This comparison does not run the gait, prove the discontinuity is visible, or establish that it is the only cause. The original IKControls, target positions, model script, and shared module were not modified. The shared module may serve other rigs, so isolate any experiment.

The prototype's read-only rig inventory was run against Dino Auto in Studio: it reported 22 Motor6Ds, no Bones, one Animator and two enabled IKControls. A subsequent read-only readiness scan reported all 22 motors missing EditRig IK metadata, with no disabled or incomplete motors; this does not reveal limits enforced by Roblox IKControls. These counts describe that inspection, not a guarantee that all transform writers have been found. The inspection code was tested; its editor button still needs interactive verification.

The experimental IKControl discovery code found four Motor6Ds for each Dino Auto leg, including the incoming hip motor. Both controllers used BasePart end effectors, so an explicit endpoint Attachment is still needed. Discovery did not change the model or disable its existing controls.

An unparented clone of Dino Auto's left and right leg chains was also checked against the source-level solver. With an illustrative nearby target and no authored limits, each solve converged and its reported endpoint matched forward kinematics within 0.000002 studs. This is a geometry test on a clone, not visible movement, an Animator coexistence test, or evidence that the real leg axes and limits are correct. `tests/studio/DinoClone.integration.luau` preserves the check.

## Current solver prototype
The portable CCD core and numerical limit handling are implemented and packaged separately from the metadata editor. Its API and coordinate conventions are in [runtime.md](runtime.md). An explicit position-only chain adapter and a manual hinge and ball joint adapter exist for Motor6D and Bone fixtures. The editor resolves a selected root-to-end path and can save an optional pole attachment. The pole heuristic, same-runtime ownership checks and temporary limit markers are prototypes; real-rig validation, external ownership arbitration and visual pose preview remain open.

## Procedural animation framework scope
The plugin should guide creators from an existing model to a controllable actor: inspect the model, choose Motor6D or Bone chains, identify root and end effectors, choose a Humanoid or AnimationController as appropriate, validate missing/ambiguous connections, and configure limits and behavior. Avatar setup should respect the existing character hierarchy and animation system. Automatic mesh skinning, uploading or changing the original source asset is a separate operation and must not be implied by this workflow.

An actor definition is versioned, serializable rig metadata with stable references, a named collection of chains, a neutral pose, and an ordered set of named behavior configurations. Behaviors are reusable modules with explicit inputs and outputs: locomotion/foot placement, look-at, reach, and secondary motion are target behaviors, not yet implemented features. The runtime composes them under one actor controller that owns selected joints, resolves priorities and weights, accepts gameplay inputs and exposes events and diagnostics. A behavior should be addable without editing generated files or framework internals. The interface must allow turning behaviors on or off, adjusting parameters at runtime, supplying targets, and extending the behavior registry from game scripts.

A setup flow should show validation and a safe reversible preview before generating an actor definition and a short editable bootstrap script. Generated scripts should reference a versioned shared framework API rather than duplicate solver code. Multiple actors should use independent state; clients and servers need a documented authority/replication policy rather than assuming a single update loop. Preview must restore transforms and any displaced controllers even on errors or plugin shutdown. The framework should report existing IKControls, Animator ownership, missing targets, invalid scales, zero-length links and disconnected chains before it takes control.

The existing experimental CCD module is one solver backend: future options include iteration budget, tolerance, damping, joint weights, pole or bend preference, and per-chain scheduling. These options need actual implementation and tests before exposure; configuration must never suggest a control is effective when it is not. Framework verification requires real Motor6D and Bone examples, actor behavior interaction, generated-script loading, save/reopen, interruption cleanup, avatar animation coexistence and multi-actor isolation. Dino Auto is a Motor6D test subject; an independent skinned Bone fixture is needed as well.

## Studio smoke evidence
A read-only Studio MCP execution on 2026-11-07 evaluated the current source for the portable limit and CCD modules in Edit mode. The single-joint antiparallel hinge test converged in one iteration with reported error 0. This is a math smoke test: no packaged module, UI, Bone or Motor6D adapter, animation, or live rig behavior was tested by that execution.

## Gameplay control SDK
A generated actor should expose a small, stable programmatic interface suitable for input bindings and other scripts: named continuous controls for joint or muscle activation, named one-shot impulses, target changes, behavior enablement and diagnostics. The authoring UI should map human-readable control names to real joints, bones, or behavior parameters and show units, range, affected chain and conflicts. A button binding should call this API; it should not need to edit generated solver code. Impulse magnitude and direction, duration, falloff, damping, limits, and blending need explicit semantics per behavior. Names are routing labels rather than proof of physical muscle simulation. Client input, server authority and replication require explicit policies.

The prototype coordinator can now retain named scalar/boolean/vector control values and deliver bounded one-shot messages to behaviors on their next step. The direct-control prototype maps scalar controls to authored hinges and vector controls to ball joints, including damped angular impulses; it does not yet simulate muscles or provide a full mapping UI. It needs real-rig verification before presenting the SDK as a finished animation control system.

## Direct-control actor prototype
The editor can generate an idle controller ModuleScript and a versioned folder containing ObjectValue references for configured Motor6D and Bone hinge or ball joints. `Runtime.createActor` consumes that snapshot only after the caller explicitly acknowledges exclusive ownership. This direct-control path is distinct from IK actor setup and remains experimental. See runtime.md for the sequence and caveats.

## Avatar compatibility
Roblox's Avatar Joint Upgrade can use AnimationConstraints instead of Motor6Ds for player avatars. The current direct-control and IK chain adapters support Motor6D and Bone only; they must detect and clearly report unsupported avatar joint types instead of claiming generic avatar compatibility. Design and integration tests for AnimationConstraint-based avatars are still needed. Roblox reference: https://create.roblox.com/docs/reference/engine/classes/Motor6D/Transform
